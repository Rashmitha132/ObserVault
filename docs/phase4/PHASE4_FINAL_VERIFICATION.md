## 4. Tenant Isolation Audit Across Database Queries

A full-codebase AST/regex scan of all `db.query(...)` calls across `backend/app/api/` was conducted.

### Primary Tenant Isolation
All primary resource lookups strictly enforce `tenant_id == current_user.tenant_id`:
- `infrastructure.py`: `db.query(Server).filter(Server.tenant_id == current_user.tenant_id)`
- `alerts.py`: `db.query(Alert).filter(Alert.tenant_id == current_user.tenant_id)`
- `incidents.py`: `db.query(Incident).filter(Incident.tenant_id == current_user.tenant_id)`
- `rca.py`: `db.query(Incident).filter(Incident.tenant_id == current_user.tenant_id)`
- `predictive.py`: `db.query(Server).filter(Server.id == server_id, Server.tenant_id == current_user.tenant_id)`
- `ai.py`: Every context builder helper explicitly filters by `current_user.tenant_id`.

### Identified Secondary Queries Without Explicit Tenancy
The audit identified five locations where secondary lookups rely on an already tenant-filtered parent record rather than explicitly adding `tenant_id` to the secondary join:
1. `backend/app/api/ml_detection.py:42`:
   ```python
   srv = db.query(Server).filter(Server.id == a.server_id).first()
   ```
   *Analysis:* `a` is an `MLAnomaly` already filtered by `MLAnomaly.tenant_id == current_user.tenant_id`. While secure in practice (since `a.server_id` was created in that tenant), defense-in-depth would dictate adding `Server.tenant_id == current_user.tenant_id`.
2. `backend/app/api/ml_detection.py:76`:
   ```python
   srv = db.query(Server).filter(Server.id == anomaly.server_id).first()
   ```
3. `backend/app/api/alerts.py:29`:
   ```python
   server = db.query(Server).filter(Server.id == a.server_id).first()
   ```
4. `backend/app/api/incidents.py:30, 35, 88, 92`:
   ```python
   server = db.query(Server).filter(Server.id == inc.primary_server_id).first()
   ```
5. `backend/app/api/egress.py:194`:
   ```python
   db_leak_check = db.query(TelemetryRecord).filter(
       TelemetryRecord.raw_metadata_json.like(f"%{sample_secret}%")
   ).count()
   ```
   *Analysis:* In `verify_privacy_filter`, this query intentionally searches the entire `telemetry_records` table to prove zero leakage cluster-wide.

## 5. Credential Redaction Test Deep-Dive

An analysis of `test_end_to_end.py` and `test_privacy.py` was conducted to clarify the exact mechanism of credential leak verification.

### What Data is Submitted
In `tests/test_end_to_end.py` (lines 35–55):
```python
raw_event = {
    "event_id": f"e2e-{uuid.uuid4().hex[:8]}",
    "timestamp": datetime.now(timezone.utc).isoformat(),
    "server_id": "srv-e2e-cluster",
    "hostname": "e2e-cluster-node",
    "collector_id": collector.id,
    "cpu_percent": 97.4,
    "memory_percent": 82.0,
    "disk_percent": 60.0,
    "network_latency_ms": 180.0,
    # Sensitive injected credentials:
    "super_secret_admin_token": "bearer_jwt_unauthorized_token_xyz",
    "db_password": "PlaintextRootPassword!456",
    "internal_ip": "172.16.4.1"
}
```

### Where Sanitization Occurs
Sanitization occurs on-premises inside the collector process via:
```python
outbound, privacy_summary = LocalPrivacySanitiser.sanitise_and_transform(raw_event)
```
`LocalPrivacySanitiser` iterates over keys and retains only fields present in `APPROVED_OUTBOUND_KEYS`. `db_password`, `super_secret_admin_token`, and `internal_ip` are discarded before the record leaves the local machine.

### What is Actually Checked in the Database
1. In `test_end_to_end.py` (lines 131–135):
   ```python
   leak_count = db.query(TelemetryRecord).filter(
       TelemetryRecord.raw_metadata_json.like("%PlaintextRootPassword%")
   ).count()
   assert leak_count == 0
   ```
   This confirms that the data written to `raw_metadata_json` does not contain the secret.
2. In `test_privacy.py` (`test_backend_pydantic_rejects_unapproved_fields`):
   Tests what happens if a compromised collector bypasses local sanitization and sends a raw password over HTTP. The backend Pydantic model (`OutboundTelemetryRecord`) has `extra = "forbid"`, which raises an HTTP 422 `extra_forbidden` validation error, preventing the raw payload from ever reaching the database.

## 6. Windows Collector Installation & Daemon Startup

Verification was conducted on `install_observault_collector.ps1` and `collector/runtime.py`:

```powershell
# install_observault_collector.ps1 (lines 60-63):
Write-Host "[5/5] Launching persistent ObserVault Collector background daemon..." -ForegroundColor Yellow
python -m collector.runtime start
Write-Host "`n>>> SUCCESS: Windows Collector enrolled and running continuously in background!" -ForegroundColor Green
```

### Automatic vs. Manual Execution Finding
- **Automatic Startup Confirmed:** The script automatically invokes `python -m collector.runtime start` upon saving `collector_config.json`.
- **Daemon Detachment:** `collector/runtime.py` spawns the collector using `subprocess.Popen` with `creationflags = 0x08000000 | subprocess.CREATE_NEW_PROCESS_GROUP` (`CREATE_NO_WINDOW`), detaching it from the PowerShell console, writing the active PID to `$LOCALAPPDATA/ObserVault/Collector/collector.pid`, and redirecting output to `collector.log`.
- **Manual Step Requirement:** The user is **not** required to run any manual startup command. However, if the user desires the collector to survive OS reboots as a Windows Service, they can optionally run `register_windows_service.ps1`.

## 8. Frontend Bundle Size & Optimization Opportunities

Running `npm run build` in `frontend/` produces:
```
dist/index.html                   1.24 kB │ gzip:   0.75 kB
dist/assets/index-B6i7xYLu.css   85.39 kB │ gzip:  12.86 kB
dist/assets/index-BeREM6r4.js   924.62 kB │ gzip: 232.09 kB
```

### Analysis
Vite warns that `index-BeREM6r4.js` exceeds 500 kB uncompressed (924 kB). However, the gzipped payload is **232 kB**, which transfers in under 50ms over standard broadband.

### Practical Optimization Opportunities (Without Altering Functionality)
1. **Route-Level Code Splitting (`React.lazy`):**
   In `frontend/src/App.jsx`, all 15 page components are imported statically. Converting them to dynamic imports:
   ```javascript
   const MLInsightsPage = React.lazy(() => import('./pages/MLInsightsPage'));
   const RootCauseAnalysisPage = React.lazy(() => import('./pages/RootCauseAnalysisPage'));
   ```
   This will divide the 924 kB chunk into small ~30–50 kB route-specific chunks.
2. **Vendor Chunk Separation via Rollup:**
   In `frontend/vite.config.js`:
   ```javascript
   build: {
     rollupOptions: {
       output: {
         manualChunks: {
           vendor: ['react', 'react-dom', 'react-router-dom'],
           charts: ['recharts'],
           icons: ['lucide-react']
         }
       }
     }
   }
   ```
   This allows browsers to cache large static libraries (`recharts`, `react`) permanently across application releases.

## 11. Remaining Risks & Operational Caveats

1. **Linux Collector Runtime:**  
   The collector codebase includes POSIX platform abstraction (`collector/platform_adapter.py`), but **no physical or virtual Linux kernel validation** was conducted in this environment. Linux support must remain designated as **experimental / unverified** until tested on a Linux host.
2. **Database Concurrency Under High Load:**  
   The default database is SQLite (`observault_saas.db`). While appropriate for single-node deployments and demonstrations, high-frequency concurrent collector writes in enterprise multi-tenant environments should use PostgreSQL (`DATABASE_URL=postgresql://...`).
3. **Repository Version Control:**  
   The project directory is not currently tracked under a `.git` repository. Source snapshots should be committed immediately upon git initialization.
